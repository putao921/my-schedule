# My Schedule —— 外观、功能与账号方案建议

面向对象：这个工具的作者本人（也是唯一用户）。
所有建议都基于当前代码的真实实现（PowerShell 5.1 + WPF、单进程、零依赖、纯本地离线），
以及本轮改动后的实际界面截图。每条都标注了**成本**与**收益**，方便你挑。

---

## 一、外观建议

### 1. 先把"语言混用"解决掉（成本低、收益最高）

现在一屏里同时出现 `Mon/Tue/Wed`、`Tasks`、`Focus`、`提交读书报告终稿`、`Today`。
混用英文表头和中文内容，是当前界面"看着乱"的最大来源 —— 比配色、间距的影响都大。

* 更具体地说，同一个"星期"概念现在有两套写法：列表视图的分组标题是中文
  （`周三 · 9月2日`，用了 `$script:DowZh`），而月视图表头还是 `Mon/Tue/Wed`
  （用了 `$script:DowShort`）。两者统一即可，改动量极小。
* 建议加一个 `Language = 'zh' | 'en'` 设置项（默认 `zh`），至少在
  *星期表头*、*视图标题*、*Tasks/Focus/Done* 这类固定文案上切换。
* **成本**：约 1 个函数 + 一张文案表（30~60 行）。**收益**：整个界面立刻协调。

### 2. 夜间模式的层级差太小（一眼能看出来的问题）

当前夜间色板里：

| 语义 | 色值 | 相邻差 |
|---|---|---|
| `Card`（卡片/格子底） | `#241A20` | — |
| `CardAlt`（表头/次级底） | `#2C2028` | 仅 8 级 |
| `Panel`（面板底） | `#35262E` | +9 级 |

8 级的亮度差在真实显示器上几乎看不出"谁是表头、谁是内容"。建议给夜间的
`CardAlt / Panel` 各拉开到 **12~16 级**（例如 `#302430` / `#3C2C36`），
月视图的空占位格、任务卡的表头就能自然分层。
**成本**：改 4 个色值。**收益**：夜间可用性明显提升。

### 3. 三个强调色放在一起时不够"分得开"

`AccentEvent #C05A6C`（红）、`AccentFocus #F2B083`（橙）、`AccentTask #9FC4A4`（绿）
饱和度接近、明度也接近，月视图里 Orange 条和红色标题条混排时容易糊成一片。
建议只动明度：让 Event 更深、Focus 更亮、Task 居中，并**只把颜色用在"必须区分"的地方**
（现在事件标题、标签芯片、按钮、左侧色条都在用色，反而都不突出）。

### 4. 周视图的密度应该可调

`HourHeight = 40`、全天 24 小时 → 轴高 960px，必须滚动才能看全一天。
对"以周为单位排时间"的人来说，40px/小时偏松。
建议加 `WeekDensity = 紧凑 28 / 标准 40 / 宽松 56`，放在周视图时段控件旁边。
**成本**：一个设置项 + 复用现有的 `New-WeekAxis`（`HourHeight` 已经是变量，改一行即可重画）。

### 5. 空状态与反馈

* 列表视图没有任何日程的区域是纯空白 → 加一句"这一周还没有安排 · 点这里新建"。
* 删除任务已经有 Yes/No 二次确认（`Remove-Task`），但**确认之后不可撤销**。建议加 5 秒内
  可撤销的提示条（Windows 自己的"删除到回收站"就是这个模式）—— 二次确认挡不住"手比脑子快"。
* 拖拽改时间、改时长时，已经有对齐虚线和时间提示 —— 这套做得很好，建议保持不变。

### 6. 一些小的一致性

* 新加的标题栏 × 是无底色轻按钮，而主窗口的窗口按钮是"有底 + 圆角"。
  两种风格都能接受，但同一套皮肤里最好统一（把 × 也加一层极浅的底色即可）。
* 像素风 + 硬阴影是这套皮肤的特色，**建议保留**：它在"日程/任务"这种小卡片场景里
  辨识度很高，比圆角扁平 UI 更有记忆点。

## 二、功能建议

按"投入产出比"分三档。

### 第一档：一两天能做完，收益立竿见影

| # | 功能 | 说明 | 为什么值得做 |
|---|---|---|---|
| 1 | **自然语言快速录入** | 在标题框里输入「明天 15:00 和导师开会 1h」，自动填日期/时间/时长 | 用的是纯本地规则（正则 + 中文数字），不需要联网、不需要 AI。手输 4 个字段降到 1 个 |
| 2 | **全局热键** | `Ctrl+Alt+N` 任何界面下唤起"快速添加"小窗 | 日程工具最大的使用障碍是"要切窗口"，热键解决它 |
| 3 | **.ics 导入 / 导出** | 导出一份可被 Outlook / Google Calendar / 手机日历订阅的文件 | 这是**免费的多设备方案**：把 .ics 放进 OneDrive，手机日历订阅它，就跨设备了，完全不需要后端 |
| 4 | **删除可撤销** | 删除后 5 秒内点"撤销"恢复刚删的日程/任务 | 现在有二次确认，但确认后无法回退；误删只能翻备份 |
| 5 | **数据自动备份** | 每次保存前把旧文件轮转成 `schedule.1.json … schedule.7.json` | 见第三节的"工程风险"，`Save-Data` 目前是直接覆盖写 |
| 6 | **键盘操作** | `↑/↓` 选任务、`Enter` 编辑、空格勾选、`/` 聚焦搜索框 | 列表视图现在纯鼠标操作 |

### 第二档：一两周，把工具从"能看"变成"能管事"

| # | 功能 | 说明 |
|---|---|---|
| 7 | **任务 → 时间块（拖到日历上）** | 从任务面板把任务拖到月/周视图，生成一条日程并回填 `dueTime` / `actualMin`。任务和日程现在还是两套数据，接上才叫"日程管理" |
| 8 | **今日计划（自动排期）** | 按优先级 + 截止 + 预估时长，从任务池里挑出今天的 3~5 件事，一键变成时间块 |
| 9 | **统计面板升级** | 现在设置窗里只有"近 7 天柱状图"。建议：专注热力图（类似 GitHub 的贡献图）、按项目/标签的周报、完成率趋势 |
| 10 | **番茄钟与任务强绑定** | `Start-FocusForTask` 已经记下了 `Pomo.TaskId`，但一轮专注结束时并没有把真实用时写回任务的 `actualMin` —— 补上这一步，"实际耗时"才不是靠手填的 |
| 11 | **例行事项 / 模板** | "每周一 9:00 组会"这类，现在靠重复日程的规则能勉强表达，但缺少"一键套用一周模板" |
| 12 | **标签/项目可自定义** | 现在 tag 固定 `work/focus/life/task` 四个，项目是自由文本（容易写错出现 `Study` / `study` 两个项目） |

### 第三档：需要后端，等真有必要再做

多设备同步、日历共享、团队协作 —— 见下一节。

### 工程健壮性（不是功能，但优先级不低于功能）

1. **写文件不是原子的**：`Save-Data` 用 `Set-Content` 直接覆盖 `schedule.json`。
   断电/强杀进程时可能写出半截 JSON，下次启动就丢数据。建议：写临时文件 → `Move-Item -Force` 替换。
2. **没有 schema 版本号**：`schedule.json` 里只有 `events` / `tasks`。加一个
   `schemaVersion`，以后改字段结构才能平滑迁移（现在改结构就得写一次性转换脚本）。
3. **JSON 转义**：PS 5.1 的 `ConvertTo-Json` 会把中文转成 `\uXXXX`。不影响功能
   （读回来正常），但人工查看/手工编辑文件时很难受。想好看的话自己包一层
   `JavaScriptSerializer` 或用 `-Compress` 后做后处理。
4. **数据规模**：现在是"全量读进内存 + 全量写回"。几千条以内没问题，
   到上万条时 `Refresh-All` 会开始卡（每次刷新都重建整个可视树）。

## 三、多账号登录与数据保存 —— 建议方案

### 3.1 先把需求拆开，三个层次的成本差 100 倍

"希望通过不同的账号登录并保存数据"这句需求，实际上可能是下面三件事之一：

| 层次 | 真实诉求 | 需要什么 | 成本 |
|---|---|---|---|
| **A. 本地多档案** | 家里/办公室同一台电脑几个人用，各看各的 | 只要文件分目录 | 半天 |
| **B. 跨设备同步** | 一个人，公司电脑 + 家里电脑 + 笔记本 | 需要一个"共享的存储"（云盘或服务器） | 1~2 天（云盘）/ 1~2 周（服务器） |
| **C. 真账号体系** | 注册、登录、找回密码、多端一致、可能共享给别人 | 服务器 + 数据库 + 运维 + 合规责任 | 数周，且**从此你有持续责任** |

**我的建议：先做 A，同时用 .ics 顺手解决 B，C 留到你真的需要共享给别人的时候再上。**
理由很简单 —— 你的工具现在是"零依赖、纯本地、不联网"的，这是它最大的优点。
一旦引入登录，你就得永久承担：服务器要花钱、数据要备份、密钥要轮换、
用户（哪怕只有你）要能删号、日程是敏感个人信息还得有隐私说明。
这个代价，只有"真的需要跨设备/多人共享"时才划算。

### 3.2 方案 A：本地多档案（推荐立刻做）

**数据布局**（从现在的单目录改成两层）：

```
%APPDATA%\MyScheduleWidget\
  accounts.json            { version:1, current:"u_8f3a",
                             list:[ {id,name,color,createdAt}, … ] }
  accounts\
    u_8f3a\  schedule.json  settings.json  avatar.dat
    u_22b1\  schedule.json  settings.json  avatar.dat
  errors.log               全局日志（所有档案共用，方便排障）
```

**改造点（对现有代码几乎是零侵入）**：

1. `$script:DataDir` 从"固定目录"变成"由当前档案决定"。
   现有代码里所有文件路径都是 `Join-Path $script:DataDir '…'`，所以**只改 DataDir 一处**。
2. 启动流程加三步：
   * 读 `accounts.json`；**若不存在而老目录里有 `schedule.json`，自动迁移成 `accounts\default\`**
     （迁移时保留一份 `schedule.json.bak`，出问题能回退）；
   * 没有 `current` → 显示"选一个档案"界面（头像 + 名字，像 Windows 的登录界面）；
   * 有 `current` → `DataDir = accounts\<id>\`，之后走原来的加载流程。
3. 切换档案 = 换 `DataDir` + `Load-Data` + `Refresh-All`（约 30 行）。
   入口放在左上角头像菜单里（那里现在只有"更换头像"，天然合适）。
4. 每个档案可以有自己的主题色/头像，视觉上一眼能分辨"现在是谁的"。

**要不要密码？** 分两种情况：
* 只是"分清楚谁是谁、互不覆盖" → **不要密码**，加了只会让你自己烦。
* 确实要防同事/家人随手打开看 → 用 **Windows DPAPI** 存校验值：
  `[Security.Cryptography.ProtectedData]::Protect(...)`，绑定当前 Windows 账户。
  **绝对不要明文存密码，也不要在 JSON 里存密码哈希** —— 本地文件哈希对有心人没有意义，
  但明文/弱哈希一旦泄露就是真实风险。

### 3.3 方案 B：跨设备 —— 两条路，建议先走便宜的

| 做法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **B1. 数据目录指向云盘**（OneDrive / 坚果云 / 百度网盘同步文件夹） | 设置里把 DataDir 改成云盘里的目录，多台设备共享 | 零代码、零成本、立刻能用 | 两台设备同时开着会互相覆盖；云盘同步有延迟；冲突只能靠"保留冲突副本" |
| **B2. 导出/订阅 .ics** | 只导出，手机/Outlook 订阅这个文件 | 只读、天然只同步"日程"不同步任务；手机端体验好 | 单向；任务还是留在电脑上 |

**B1 的必做防护**：加一个"检测到文件被外部修改就提示重载"的机制
（记录 `LastWriteTime` + 文件大小，启动/定时比对），否则你会静默丢数据。

**如果将来要做真正的双向同步**，正确的做法不是"同步整个 JSON 文件"，而是：
* 每条记录带 `id`（已有）+ `updatedAt` + `deleted` 软删除标记；
* 同步时按 id 做集合合并（谁的时间戳新听谁的），删除用墓碑标记；
* 这样才有合并的可能。整文件覆盖的做法在两端同时编辑时必然丢数据。

### 3.4 方案 C：真账号体系（如果一定要做）

技术选型只有两类，**都别自己从零写 HTTP + 数据库 + 密码学**：

| 选项 | 适合场景 | 备注 |
|---|---|---|
| **托管后端**（Supabase / Firebase / 腾讯云开发 / 本环境可用的 WorkBuddy 云服务） | 想要"邮箱或手机验证码登录 + 云数据库 + 文件存储"，不想碰运维 | 有免费额度；内置行级权限；能直接给出"每个用户只能读写自己的行"的策略。**首选** |
| **自建轻量后端**（Cloudflare Workers + D1、腾讯云函数 + MySQL） | 想完全掌控、或有内网/私有部署要求 | 要自己处理 HTTPS 证书、密钥管理、备份、监控 |

**客户端（这个 PS 程序）侧的关键约束**：
* **离线优先**：登录态不能让"断网就打不开日程"。正确姿势是本地文件仍是主数据源，
  登录只负责"把本地改动推上去 / 把云端改动拉下来"，断网时标注"待同步"。
* **不要把长期密钥/服务端密钥写进客户端**：PowerShell 脚本是明文可读的，
  任何写死在里面的 key 都等于公开。要用一次性/短时效 token。
* **传输出口只走 HTTPS**，且要能一键关闭同步（隐私开关）。
* **做好"删号"和"导出"功能**：这既是合规要求，也是你将来换方案时的退路。

### 3.5 推荐的落地顺序

```
第 1 步（半天）  本地多档案 + 自动迁移 + 头像菜单切换
                 → 满足"不同账号登录、各自保存数据"的字面需求，且完全离线
第 2 步（半天）  .ics 导出 + 数据目录可自定义
                 → 手机/其他电脑能"看到"日程；同时为云盘同步铺路
第 3 步（1 天）  原子写 + 轮转备份 + schemaVersion
                 → 一旦开始跨设备，数据损坏的代价会放大 10 倍，必须先做这个
第 4 步（按需）  接托管后端做真登录（邮箱/手机验证码）+ 按 updatedAt 合并
                 → 到这一步之前，都不需要服务器
```

**一句话结论**：你要的"不同账号登录并保存数据"，如果只是**同一台电脑上互相隔离**，
本地多档案就够了，半天能做完、零风险、纯离线；如果是要**跨设备**，
先做 .ics + 云盘目录这两件"零后端"的事；等真的需要**多人共享同一份日程**时，
再上托管后端，并且那时必须先补齐备份、原子写、软删除合并这三件底层功课。

# 第二轮：改完这四项（窗口自适应 / 月视图补齐 / Tasks 独立视图 / Focus 可拖动）之后的建议

上面那部分是**改造之前**写的。这一部分是在这四项都做完、并且跑完全套回归

有新东西要说的原因很简单：**改动本身会把原来藏着的毛病推到台面上**。
下面 5.1 里的三条就是这轮"顺带发现"的 —— 它们都不是新写的代码引入的，

## 五、先修这三件"这轮顺带发现的既有问题"

### 1. 筛选条件和搜索词，切一次视图就没了（优先级最高）

**事实**（代码路径，不是猜测）：

```
点侧栏 → Set-View 'tasks'
       → $script:Settings['View'] = 'tasks'; Save-Settings
       → Refresh-All
            ├─ $script:TaskStatusBox = $null   （连搜索框一起置空）
            └─ Render-Tasks → 重新 new 一个下拉，SelectedIndex = 0
                             重新 new 一个搜索框，Text = ''
```

`Render-Tasks` / `Render-List` 里那几个筛选控件是**每次刷新都新建**的，
新建时 `SelectedIndex` 被写死成 0、`Text` 写死成空。于是：

* 你在 Tasks 里筛了「Open」，转头去周视图看一眼，回来变成「All status」；
* 列表页的「Work」标签筛选、「Focus」范围筛选、搜索词，同样一轮就重置。

这不是"忘了保存"，而是**筛选状态根本没有任何地方存过**。
对"每天要重复看同一个筛选"的人来说，这是实打实的重复劳动。

**建议**：加一个**会话级**（不进 settings.json，重开程序就重置）的筛选状态表：

```powershell
$script:TaskFilter = @{ project = 'all'; status = 'all'; scope = 'all'; sort = 'due'; q = '' }
$script:ListFilter = @{ tag = 'all'; scope = 'all'; q = '' }
```

* `Render-Tasks` / `Render-List` 建完控件后，按这张表回填 `SelectedIndex`（用
  `Tag` 反查，不要写死下标 —— 项目下拉的选项是动态的，写死下标一定会错位）；
* 各 `Add_SelectionChanged` / `Add_TextChanged` 里先写回表、再调 `Fill-Tasks`。

**成本**：约 30 行，集中在 3 个函数里。**收益**：切视图不再"白干一遍"。
**注意**：一定用 `Tag` 反查而不是下标，这是唯一容易写错的地方。

### 2. `HourHeight` 会出现 61.5 这种半格值（像素风会糊）

**事实**：这轮新加的 `Fit-WeekAxisHeight` 里有一行

```powershell
$want = [math]::Round($want * 2.0) / 2.0     # 吸附到 0.5
```

也就是允许 `61.5` 这样的值。逻辑上没问题（时间映射全按浮点算），
但**像素风皮肤是画 2px 实线的**：轴高 738 像素时，小时线和"每 30 分钟"的
中间线会落在 x.5 上，100% 缩放的真实屏幕上会表现为"有的线 2px、有的线 3px"，
截图里看不出来（截图是整数像素取样），真机上看着就是不齐。

**建议**：把吸附单位从 0.5 改成"能被 30 分钟整除的偶数"：

```
候选集：40 44 48 52 56 60 64 68 72    （每档 30 分钟的格子高 = 候选值/2，都是偶数）
选法：取 ≤ 目标值的最大候选；目标值 < 40 时取 40（保持既有密度兜底）
```

再补一条**上限**：24 小时视角下最高不超过 `64`（约 1536px 轴高），
超过就把余量留在上下留白，而不是继续拉伸 —— 否则在很高的窗口里，
"全天 24 小时"会变成一条条色带，反而不像日历了。

**成本**：只改 `Fit-WeekAxisHeight` 一个函数（约 15 行，含候选集）。
**收益**：像素风的线条在各种窗口高度下都保持锐利。

### 3. 搜索框的占位提示是"叠"出来的，以后再碰输入框要小心

这轮刚给列表页和 Tasks 页的搜索框加了占位提示（`Search task titles…` /
`搜索日程标题…`）。WPF 的 TextBox 到 .NET Framework 4.x 都没有原生 Placeholder，
所以用的是：**底色画在外层 Grid 上 → 输入框自身透明 → 提示文字垫在输入框下面**。

提示就会被**整块盖住**（界面上看就是"没做提示"，而可见性逻辑却全部通过）。
审计里那条 `search box placeholder` 会把这种回归挡下来 —— 它同时断言了
"输入框背景 alpha = 0"，别把它删了。

### 1 里面真正花时间的不是布局，是"双击这条路本来是死的"

详情面板里有一行（`Views.ps1`，展开分支内）：

```powershell
$addLine = { param($Label,$Value) ... New-Txt ... -Color (Get-Pal 'InkFaint') ... }.GetNewClosure()
```

`GetNewClosure()` 会把脚本块**复制进一个新的动态模块**，而动态模块的函数表只有 `global`
作用域 —— 面板里调的 `Get-Pal` / `New-Txt` 都是脚本作用域里的函数，在那个模块里一律
`CommandNotFoundException`。这个 bug 之所以难发现，是因为三个条件必须叠在一起：

1. 不展开就走不到这段代码 → 平时一切正常；
2. 只有双击才展开；
3. 抛出点在 `Fill-Tasks` 的 **`Children.Clear()` 之后** → 任务列被清空、又没重建回来。

**所以用户看到的现象不是"双击没反应"，而是"双击之后整列任务都消失了"。**
他自己描述成"没有唤醒修改菜单"，其实是在看一个已经空掉的列表。

顺手把 `Fill-Tasks` 改成"先把新卡片建进本地列表，整轮无异常再一次性换上去"（原子替换）。
以后任何一张卡片渲染抛异常，最坏也只是画面停在上一帧（旧数据但可读），不会再变成一片空白。

### 顺带修掉的两个"假绿灯"

这两个都不是用户报的，但不修的话**以后每次改动都会被测试误导**：

**(a) 三个函数的参数都叫 `$Args`，与 PowerShell 自动变量 `$args` 同名冲突。**
`$args` 是"未绑定参数数组"，同名参数会在函数入口**被绑定器覆盖成 `@()`** ——
实参明明传进来了，函数体里读到的却是一个空数组。实测
（`verification\_args_probe.txt`，可复跑）：

```
param($Args) 读 .ClickCount -> 在此对象上找不到属性“ClickCount”（StrictMode 2.0 下硬抛）
param($X)    读 .ClickCount -> 2
```

被 `try/catch` 吞掉后就**静默降级**成兜底值，测试全绿。实际后果三个：

* `Get-MouseClickCount` 永远返回 `1` → **所有"双击"分支失效**；
* `Get-EventSourceOf` 永远走不到 `OriginalSource`（退化成兜底）；
* `Test-ClickOnButton` 永远返回 `$false` → "点 × 别拖窗口"的护栏一直是空转的。

周视图的"双击编辑事件"和"空白拖拽新建"就是被这个打哑的。
而任务卡双击**恰好**走了 `$script:SyntheticClickCount` 旁路、在读到 `$args` 之前就返回了，
**把这个 bug 完整地盖住了** —— 这才是它能在 93 条断言下活下来的原因。

**(b) `Get-EventSourceOf` 的 `$Fallback` 参数传了却从来没用过。**
调用方全都写了 `Get-EventSourceOf $e $s`，但函数最后一律 `return $null`。
等于每个调用点都在"认真传兜底、函数认真忽略"。已补成
`旁路 → OriginalSource → Source → $Fallback` 的完整链路。

## 十三、这轮的三个坑有共性 —— 建议固化成规则

这三条不是"再小心一点"就能解决的，它们各自需要一条**机器来执行的**规则。

### 1. 作用域类：在自己的作用域里跑得好，换个调用上下文就静默失效

`GetNewClosure()`、`param($Args)`、处理器里忘了写 `$script:` —— 是同一类问题。
已在 `verification\SyntaxCheck.ps1` 里加了两条**静态硬错误**：

* 禁止 `.GetNewClosure()`
* 禁止把函数参数命名为 `$Args`

并且两条都做了**负向测试**（故意把坏代码写回去，确认规则真的报错、而且只报这一处）。
这一步很关键：`ClosureScan.ps1` 的头注释**早就写了**"GetNewClosure() 不能用"，
但知识没有被强制执行，同一个坑又被写了一次。
**一句话：没做过负向测试的静态规则，等于没有这条规则。**

### 2. 失败模式类："先清空再重建"会把局部异常放大成整页空白

`Fill-Tasks` 是这个模式，值得全局扫一遍同类渲染（月/周/列表页的 host 都是
`Children.Clear()` 再逐块加）。建议统一改成原子替换。
**判断标准**：如果这个函数抛异常，用户看到的是"一片空白"还是"上一帧"？前者都应该改。

### 3. 假绿灯类（最值得警惕）：测试走了旁路，真实路径从来没被执行过

这是本轮最有价值的发现。任务卡双击的测试一直用 `$script:SyntheticClickCount` 旁路注入
ClickCount，所以它**从来没走过真实的 `$Args.ClickCount` 那一行** ——
`param($Args)` 的 bug 因此可以对 93 条断言完全免疫。

→ **建议：每引入一条旁路（bypass / synthetic 注入），就同时补一条"不走旁路"的断言。**
哪怕那条断言只是"证明旁路为空时代码也不炸"。
这轮用的是"在处理器里同时打印 `cc=`（走函数）和 `raw=`（直读属性），两者不一致就立刻暴露"。

## 十七、这一轮做的三件"看起来小、实际很关键"的事

### 1. 字号体系：为什么用"档位"而不是滑块

设置里调字号，第一反应是给个 5%~200% 的滑块。这个项目**没这么做**，理由有三条：

* **滑块调不出"和默认一样"**。用户想回到初始状态时，只能靠肉眼估摸；档位里有一个
  明确的 `Normal`，点一下就回去了。
* **半像素字号会让像素风发虚**。WPF 在非整数 DPI 下渲染文字本身就会做对齐，
  再叠上一个 13.37px 的字号，小数部分不可控。所以 `Scale-Ui` 内部**向上取到 0.5 的整数倍**
  （`[math]::Round($r * 2.0) / 2.0`）—— 宁可差半像素，也不要发虚。
* **档位可以和"自适应"合成**。`UiScale = 用户档位 × 窗口自适应`，
  两个维度正交，用户理解成本低：一个是"我就喜欢大字"，一个是"跟着窗口走"。

**这条对用户第 4 条的意义**：自适应因子只有三档（0.90 / 1.00 / 1.08），
刻意不做成连续的。因为窗口宽度在拖动时是连续变化的，如果字号跟着连续变，
用户每拖一下像素就会看到文字在"呼吸"，比不变还难受。三档意味着
**跨过阈值才跳一次**，视觉上是一次干脆的重排。

### 2. 弹窗按钮语义：为什么 Save 是"转发给 ×"而不是各写一套

`Bind-DialogChromeButtons` 里，Save 按钮的处理器做的事情是：
**手工给 × 触发一次 `Click` 事件，然后 `$e.Handled = $true` 吞掉自己的这次**。

```powershell
$save.Add_Click({
    param($s, $e)
    $hit = $s.Tag['close']       # 引用走 Tag，不读局部变量（处理器作用域已销毁）
    $hit.RaiseEvent((New-Object System.Windows.RoutedEventArgs(
        [System.Windows.Controls.Primitives.ButtonBase]::ClickEvent)))
    $e.Handled = $true
})
```

**为什么不给 Save 单独写一遍保存逻辑**：因为 × 的处理器里已经有完整的
"读控件 → 校验 → 落库 → 关窗"流程。如果 Save 再抄一遍，两处就会**各自演化** ——
下次给设置加一个字段，很容易只改了一处，于是"点 Save 保存了、点 × 没保存"
（或者反过来）。转发只有一条真实路径，行为必然一致。

**这里的坑**（第三轮踩过、这轮规避）：处理器里**不能读创建函数的局部变量**，
因为处理器触发时那个作用域已经销毁了。所以引用的传递方式是
`$save.Tag = @{ kind='dlg-save'; close=$close }`，处理器只读形参 `$s`。

**断言怎么证明转发真的成立**：不能只断言"点 Save 之后设置存进去了" ——
那只证明了"存了"，没证明"走的是 × 那条路"。所以断言里同时验
`点 Save` 和 `点 ×` 的结果**在数值上完全一致**，并且专门验
**Cancel 之后设置一个都没变**。第三条是防"Save 和 Cancel 被误接成同一个处理器"，
这种情况下前两条依然全绿，用户却会发现"点 Cancel 它还是给我存了"。

### 3. Cancel 的验收：为什么要一次验 7 个字段

设置项涨到 7 个之后，"Cancel 不保存"就有了 7 个可能的漏点。
只验番茄钟一个字段（第三轮的做法）挡不住新字段的遗漏。

第四轮的做法是 `settings cancel saves nothing`：**一次性改满 7 个字段再 Cancel**，
逐个断言复原。这条断言的诊断输出会把 7 个字段的当前值全打出来
（`theme=light scale=1 top=False tray=False range=0-24 pomo=25`），
一旦哪个漏了，从输出直接能看出是哪一个。

## 十八、这一轮的新坑：`Bind-DialogChromeButtons` 首版是"静默失效"的

值得单独记一笔，因为它和第三轮的坑**是同一个成因**。

首版代码在处理器里直接读创建函数的局部变量：

```powershell
# 错误写法（首版）
$save.Add_Click({ $close.RaiseEvent(...) })   # $close 在触发时已不存在
```

在 `StrictMode 2.0` 下这会抛异常，而外面套着 `try/catch`，异常被**吞掉**了。
表现是：**点 Save 完全没反应**（不报错、不崩溃，就是不动）。

这和第三轮的"`param($Args)` 被自动变量覆盖成 `@()`"是同一类问题：
**在自己的作用域里跑得好，换个调用上下文就静默失效**。
区别是这轮找不到"`$args` 覆盖"那样明确的机制，只能靠"引用一律走 `$s.Tag`"
这条**约定**来防。

**这条约定现在已经写进第六节的规则里**：

> WPF 事件处理器里需要的外部引用，一律通过 `$s.Tag`（或 `$script:`）传递，
> **不许**直接捕获创建函数的局部变量。

## 十九、`SyntaxCheck.ps1` 新加的静态规则：裸字号不许再增加

第四轮给字号体系加了静态防线：

```
[OK  ] 裸字号没有增加（23/23 处，均为第四轮前的既有写法；新增请用 New-Txt 或 Scale-Ui）
```

规则匹配 `\.FontSize\s*=\s*\d` —— 也就是"**直接赋一个数字字面量**"。
走 `Scale-Ui`、走变量、走 `[math]::Round` 换算的一律放过。

**为什么是"上限"而不是"全禁"**：`Views.ps1` 的 `New-EditorField` 系列、
`Views2.ps1` 的弹窗输入框、`Care.ps1` 的右键菜单，一共有 23 处这种写法。
它们都是"内层小字/输入框"，字号本身不大，而且旁边的 `Height` 也是写死的。
一次性全改会牵动大量布局，回归面太大、收益不成比例。

所以这条规则钉的是**增量**：

* 旧代码保持原样 → 总数 23，报绿
* 谁再手写一个裸 `FontSize = 14` → 总数 24 > 23，报红，并把**全部 24 处**列出来

**做了双向验证**（这是关键，只跑正例证明不了规则有效）：
正例 `23/23 PASS`；负例往 `Care.ps1` 尾巴插一个探测函数，
立刻报 `[BAD] 裸字号比基线多了 1 处（24 > 23）` + `结论: FAIL`，
探测函数还原后回到 `PASS`。

**下轮建议顺手做的**：把 `New-EditorField` 系列内部改成走 `Scale-Ui`，
然后把这个上限从 23 一路压到 0。那时规则就可以从"上限"升级成"全禁"。

## 二十三、本轮新建议

### 1. 设置窗口该分页了（现在是最长的那个短板）

第五轮又往设置里塞了两个下拉（语言、密度），它现在是 **9 项一条长滚动**。
截图 `r7-*` 里设置窗口已经要滚两屏。下一轮再加东西之前，建议先分页：

* `外观` —— 字号、主题、语言、周视图密度
* `窗口` —— 置顶、关闭到托盘、周时段
* `数据` —— 数据目录、导出、备份
* `关于` —— 版本、快捷键说明

这件事的价值不在"好看"，而在**它决定了后面还能不能继续加设置项**。
不分页的话，再加 3 项就会变成"找一项设置要滚半天"。

### 2. 语言只统一了"框架词"，内容还是混的

这是有意留的边界（第二十节记过），但值得说清楚现状与下一步：

* **已经统一**：星期、月份、导航、视图标题、空状态、撤销提示、每日一句的标题。
* **还没统一**：所有**弹窗里的字段名与按钮**（`Title` / `Date` / `Start` / `Repeat` /
  `Save` / `Cancel` …）、任务卡上的 `Focus` / `Work` / `Time`、
  菜单里的 `Open data folder`、Toast 的其它文案。

判断标准很实用：**你截一张图，如果框架是中文而字段是英文，看着还算舒服；
如果弹窗里也是中英夹杂，那才是真的乱。** 建议下一轮把弹窗字段表也接进
`Get-LangText` —— 弹窗文案数量有限（约 40 条），一次能做完。

### 3. 密度应该记住"每个视图"的偏好，而不是全局一个值

现在是全局 `WeekDensity`。但真实使用里，**月视图想紧凑、周视图想宽松**是很常见的
矛盾需求 —— 月视图看全貌，周视图看细节。建议改成 `WeekDensity` +
`MonthDensity` 两个键，月视图的格子高度也走倍率。

顺带一提：`DensityGrowMax = 1.6` 这个放大上限是本轮为了"紧凑档别被窗口拉成 220px"
加的保护。**如果你把窗口拉得很高又想保持紧凑，可能会觉得"没长到该有的高度"** ——
那说明该调的是这个上限（1.6 → 2.0），而不是密度档本身。这个数值得你自己试。

### 4. 撤销只留一次，且不跨视图

现在 `$script:UndoState` **只保存最近一次删除**，而且切换视图 / 重启就没了。
这是刻意的（"多级撤销与本工具体量不成比例"），但有两个场景会咬人：

* **连续删两项** → 只有第二项能撤。
* **删完切到别的视图再想撤** → 提示条还在（5 秒内），但心里已经没底了。

如果要再走一步，建议做成**一条 3~5 步的操作栈**（不只删除，勾选完成、
拖动改时间也可以进去）。这是"日程工具"和"日程工具 + 安全感"的分界线。

### 5. 撤销提示条的位置是硬写的，多显示器下会跑偏

`Show-Toast` 里 `Left = $wa.Right - 320` 用的是**主屏**工作区。
接了副屏、或者把主屏设在右边时，提示条会出现在副屏或者屏幕外。
建议存成设置项（`ToastCorner = 右下 / 左下 / 跟随主窗口`），
或者干脆跟随主窗口右下角 —— 用户看的人始终是那个窗口。

### 6. 一个本轮踩到、值得记下的工程坑（不是外观建议，但影响后续开发）

中文月短名最初是让调用方对 `MonNames` 做 `.Substring(0,3)` 取前三个字符
（`September → Sep`）。切到中文后 `MonNames` 变成 `"9月"`（**2 个字符**），
`.Substring(0,3)` 直接**抛越界**，整个 Boot 崩掉、`errors.log` 里只有一行
`Boot-dispatch: 使用"2"个参数调用"Substring"时发生异常`。

**结论**：凡是"从数组里切字符串"的写法，都要先问"这个数组换语言/换数据源之后
长度还够不够"。修法是**让短名独立成一个数组**（`$script:MonShort`），
调用方不再自己切。这类问题在切换数据源时最容易漏 —— 静态检查也看不出来。
